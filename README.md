# Gladys Assistant – Text2Speak

External Gladys Assistant integration for [Text2Speak](https://github.com/jeanbruder/Text2Speak), the multi-room text-to-speech service.

**Main feature:** a scene action with three independent parameters:
1. Message text (Gladys scene variables are resolved by Gladys before the integration receives the action).
2. Priority from `0` (highest urgency) to `9` (lowest urgency).
3. Target rooms/zones (comma-separated); leave empty to use Text2Speak's configured default.

The integration sends `POST /dire` and validates explicit targets against `GET /pieces`.

## Requirements

- Gladys Assistant 5.1.0 or later.
- Text2Speak API reachable from the Gladys integration container.
- Node.js 24 recommended for local development.
- Docker for image builds.

Text2Speak's current API does not provide authentication. Keep it on a trusted LAN; do not publish port 1337 to the public Internet.

## Configure in Gladys

Set the API base URL in the integration Configuration tab, e.g.:

```text
http://192.168.1.50:1337
```

Use the LAN address of the Text2Speak host. `localhost` inside the integration container refers to the integration container itself, not the Gladys host or the separate Text2Speak host.

Click **Test Text2Speak connection** to check `GET /pieces` and display the number of rooms and zones found.

## Scene action

In the Gladys scene editor, find **Integrations → Text2Speak → Speak a message with Text2Speak**.

| Field | Meaning |
|---|---|
| Message | Text to speak; Gladys variables are supported |
| Priority | Integer 0–9; 0 is the most urgent |
| Rooms / zones | Comma-separated Text2Speak keys; blank uses Text2Speak default |

Examples of target field values:

```text
salon
salon, cuisine
rez_de_chaussee
maison
```

Targets are checked against the `pieces` and `zones` objects returned by Text2Speak's `GET /pieces` endpoint. The current Gladys scene-action field schema does not provide a runtime-populated list for arbitrary API values, so this field is deliberately a text field with live validation.

The Text2Speak API accepts the following payload:

```json
{
  "dire": "Le repas est prêt",
  "priorite": 5,
  "cibles": ["maison"]
}
```

If targets are blank, `cibles` is omitted entirely so Text2Speak applies its own `defaut` configuration.

The `202 Accepted` response means the message has entered the Text2Speak queue. The scene action returns:
- `job_id`
- `queue_position`

It does not wait for playback to finish. Text2Speak's `GET /file/<id>` endpoint provides the later playback status.

## Local development

```bash
npm install
npm test
npm run check:manifest
```

Run against a Gladys development installation:

```bash
GLADYS_HOST_API_URL="http://127.0.0.1:1443" \
GLADYS_INTEGRATION_TOKEN="YOUR_TOKEN" \
GLADYS_INTEGRATION_SELECTOR="gladys-text2speak" \
LOG_LEVEL=debug \
npm start
```

Use the token and selector generated by Gladys developer mode. Do not commit them.

## Docker build

```bash
docker build -t gladys-text2speak:dev .
```

Gladys 5.1+ developer mode can install a local Docker image directly from the local Docker daemon. For testing, build the image on the machine that runs Gladys.

## GitHub publication

1. Create a **public** GitHub repository named `gladys-text2speak`.
2. Copy the project files into it.
3. Check the `docker_image` value in `gladys-assistant-integration.json`. It must match the GitHub owner and repository name. The initial manifest is set to `ghcr.io/jeanbruder/gladys-text2speak:1.0.0`; change `jeanbruder` if publishing under another owner.
4. Add the GitHub repository topic `gladys-assistant-integration` in the repository About settings.
5. Push the repository's default branch.
6. Create and push a release tag:

```bash
git add .
git commit -m "Initial release"
git branch -M main
git remote add origin https://github.com/JEANBRUDER/gladys-text2speak.git
git push -u origin main

git tag v1.0.0
git push origin v1.0.0
```

The `Publish Docker image` workflow builds and publishes a multi-architecture image (`linux/amd64` and `linux/arm64`) to GitHub Container Registry (GHCR).

After the first publication, open the package settings on GitHub and change the GHCR package visibility to **Public**, so Gladys can pull it anonymously.

The `Validate` workflow runs the Node.js tests and the Gladys integration-store manifest validator on pushes and pull requests.

### Releasing a new version

For a new release:
1. Update `version` in `package.json`.
2. Update `version` and `docker_image` in `gladys-assistant-integration.json`.
3. Commit and push those changes.
4. Push the matching tag, e.g. `v1.1.0`.

The publish workflow then publishes `ghcr.io/<owner>/<repository>:1.1.0` and `:latest`.
